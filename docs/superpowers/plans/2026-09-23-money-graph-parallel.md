# Money Graph Parallel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Метод исполнения в этой команде:** четыре участника работают параллельно в своих инструментах. Поднавыки из строки выше относятся к агентному исполнителю при их наличии; для человеческой команды они не являются зависимостью. Этот документ не запускает агентов и не выполняет код проекта.

**Goal:** За пять часов собрать воспроизводимый локальный инструмент AML-исследования с формальными ролями, кластерами, приоритетами, интерактивным графом и двумя ограниченными AI-режимами.

**Architecture:** Один Python-проект с расчётным ядром, FastAPI и AI-модулем; отдельный React-интерфейс. Полный расчёт сохраняет законченный набор файлов, который сервер выдаёт интерфейсу и использует для AI-проверок. Все обязательные результаты создаются локально.

**Tech Stack:** Python, pandas, PyArrow, NetworkX, FastAPI, Pydantic; React, TypeScript, Vite, Cytoscape.js; один выбранный API-провайдер.

**Spec:** [согласованная архитектура](../specs/2026-09-23-money-graph-design.md). Все участники также читают [контракт v1](../../contracts/money-graph-v1.md).

## Global Constraints

- Полный пересчёт от исходных parquet до всех обязательных выгрузок — не более 300 секунд локально, без использования готовых результатов предыдущего запуска.
- Для каждого исходного узла: одна основная роль из `consolidator / transit / distributor / terminal / coordinator / peripheral`, формальное объяснение и score.
- Топ содержит минимум 20 различных узлов, если во входе их не менее 20; каждый имеет основание приоритета.
- Внешние персональные и другие атрибуты не добавляются. Все формулировки о назначении и ролях — гипотезы.
- Нулевые исходящие при обрезанном обходе недостаточны для terminal.
- Данные, карточки и AI-основания связаны одним `run_id`. Не допускается смесь результатов разных запусков.
- Обязательные объяснения и гипотезы кластеров создаёт локальное ядро. Недоступность AI не блокирует обязательные выгрузки и демо основного сценария.

## Статус решений и предел готовности плана

Архитектура утверждена. Контракт и план готовы для совместной проверки и старта независимых работ. Реальных parquet в репозитории нет; исходные имена колонок неизвестны. Формулы шести ролей, score, конфликтов, кластеризации и приоритета не были согласованы в разговоре.

Поэтому первая задача A — получить схему и предложить математическую спецификацию для короткого утверждения тимлидом. До её утверждения можно писать загрузку, агрегаты, контракт, интерфейс, API и AI-обвязку. Финальные правила не выдаются за уже принятые. Это явная зависимость, а не разрешение придумывать ответы по конкретным gid.

## Review Focus

1. Обрезанный узел без исходящих и seed с неполным входом: соответствующие условия правил не должны трактовать пропуск как достоверный ноль. Проверяет A.
2. Строковые gid с ведущими нулями, неизвестный gid и изолированный узел: идентичность сохраняется во всех слоях. Проверяют A, B и C.
3. Новый расчёт и незаконченные файлы: сервер обслуживает только один законченный запуск; AI-запрос со старым run_id получает 409. Проверяет B.
4. Слишком большой подграф: UI сообщает об ограничении и сохраняет выбранный узел; метрики остаются метриками полного наблюдаемого графа. Проверяют B и C.
5. Провайдер недоступен или модель прислала неизвестную функцию/основание: срабатывает локальный fallback, состояние результатов не меняется. Проверяет D вместе с B.

## Зависимости и параллельность

```text
Контракт v1 ─┬─ A: parquet → метрики → утверждённые правила → артефакты
             ├─ B: фикстуры → API → загрузка настоящих артефактов
             ├─ C: тестовые ответы → экран → настоящий API
             └─ D: тестовые функции → два AI-режима → настоящий Store
```

Фикстуры используются только в явно обозначенном режиме разработки. Запуск сдаваемого приложения и production-команда расчёта работают на настоящих parquet. Первый сквозной пример не означает завершение всех аналитических правил.

## Точки интеграции

- **К 20-й минуте:** один контракт, владельцы и запускаемые каркасы.
- **К 60-й минуте:** UI показывает общий тестовый узел через API; explain имеет fallback; A показывает реальные агрегаты.
- **К 120-й минуте:** один настоящий узел проходит parquet → артефакты → API → граф и карточку. Первый полный расчёт создаёт обязательные файлы.
- **К 180-й минуте:** обязательный сценарий работает на всём наборе; AI выполняет проверку с показанным основанием.
- **К 240-й минуте:** остановка добавления функций. Остаются исправления, чистый запуск, README и репетиция.

## Если участников трое

Объединить B и D. Сохранить explain и investigate с меньшим набором функций: `get_node` и `check_concentration`; общий лимит три вызова остаётся. Автоматический прогон нескольких провайдеров, дополнительные визуальные эффекты и расширение функциональности исключаются первыми.

## Если отстаём

1. Нет настоящих артефактов к 120-й минуте: A и B вместе закрывают один полный проход; C продолжает экран на контракте; D останавливает расширение AI.
2. UI тормозит: уменьшить лимит отображения, остановить непрерывную симуляцию раскладки, оставить поиск и окружение узла. Расчёт продолжает охватывать все узлы.
3. AI нестабилен: оставить локальные объяснения и explain; investigate доступен только для одной проверенной функции. Статус деградации показан явно.
4. Пересчёт медленный: измерить стадии, убрать повторные проходы и пересчёты интерфейса; тяжёлые метрики заменить только после изменения методологии и проверки влияния на роли.
5. Любое сокращение сохраняет все must-have: шесть допустимых ролей, формальные правила и score, кластеры с гипотезами, топ ≥20, поиск gid, выгрузки и воспроизводимый запуск.
