## Реализованная независимая часть

Работают `io.py`, `audit.py`, `features.py`, `checks.py` и команды `inspect` /
`audit` в `cli.py`. Аудит читает три явно сопоставленных файла, проверяет
целостность и обе таблицы денег, сохраняет изоляты и рассчитывает семь
контрактных метрик. `check_concentration` принимает словари или объекты
EdgeRecord участника B. Самопереводы фильтруются один раз на входе;
функция проверки получает уже тот же отфильтрованный список.

CLI сохраняет отчёт атомарно, не заменяет существующий файл и возвращает
код 2 при ошибке. Расхождения доступны в отчёте и при отказе расчёта.
Хеши входа проверяются до и после обработки; изменение файла требует
повторного запуска. Результат имеет `status=audit_only`, не содержит
назначенных ролей и не публикует `manifest.json` со статусом complete.

На этом этапе `config/input_mapping.json` и `config/rules.json` специально
имеют ожидающий статус. Это предотвращает применение выдуманной схемы
или неутверждённых правил. Модули ролей, кластеров, приоритета и финальный
`run_pipeline` будут реализованы после согласования; команда полного
прохода из исходного плана пока недоступна.

NetworkX 3.4.2, pytest 8.3.5. Совместимость импорта и `pip check` проверены.

Здесь `include` — явно указанный вариант предварительного аудита, а не
согласованная финальная политика. Для сравнения можно отдельно запустить
`exclude` с другим именем отчёта. Production-классификации эти команды не делают.

Формат mapping показан в синтетических тестах `tests/analytics/test_cli.py`
и `test_io.py`: `status=approved`, `dataset_kind=real|synthetic`,
`money={unit:KZT,scale:2}`, `amount_source=edges|transactions`,
`reconciliation=error|report`; `tables` содержит nodes, edges и transactions.
Для каждой таблицы задаются отдельный файл, `gid_type=string|integer` и
словарь canonical→source `columns`. У рёбер `kind=aggregate|event`, у
транзакций `kind=event`. Агрегат требует `tx_count`; событие считается
одной операцией. По умолчанию двоичные float отклоняются. Источник в
целых минимальных денежных единицах или с иной точностью потребует
явного преобразования после изучения реальной схемы.

## Вход и суммы

Сначала читаются схемы parquet, затем утверждается явное сопоставление полей.
Имена исходных колонок не угадываются. Строковые `0007` и `7` — разные узлы.
Числовые идентификаторы разрешаются только явной настройкой входного типа.
Дубликаты уникальных id, отсутствующие вершины и неверные денежные значения
останавливают обработку с диагностикой. Повторные события без id сохраняются.

Источник денег (`edges` либо `transactions`), денежная единица, масштаб,
семантика строк и ключ транзакции устанавливаются после получения схем.
Два источника никогда не складываются. По каждой направленной паре сверяются
суммы и количества. Расхождения фиксируются в аудите.

Суммы считаются точно, без двоичного float и округления исходных значений.
Флаги наблюдаемости берутся только из подтверждённых исходных полей. Из seed
и расстояний самостоятельно не восстанавливается утверждение о полноте.
Неизвестное значение сохраняется как `null` с пояснением.

**Предложение по самопереводам:** исключать их из аналитического графа и всех
его метрик, включая концентрацию; точные суммы и количества исключений
сохранять в audit. Это также означает отсутствие этих пар в `edges.json`.
Решение требует утверждения; до него аудит допускает оба явных варианта.

## Уже определённые контрактом метрики

| Обозначение / поле | Формула и смысл |
|---|---|
| `ki` / `in_degree_unique` | Число разных наблюдаемых отправителей |
| `ko` / `out_degree_unique` | Число разных наблюдаемых получателей |
| `tx_in_count`, `tx_out_count` | Сумма количеств входящих/исходящих операций |
| `I` / `in_amount_kzt` | Сумма наблюдаемых входящих переводов |
| `O` / `out_amount_kzt` | Сумма наблюдаемых исходящих переводов |
| `r` / `out_in_ratio` | `O / I`, если `I > 0`, иначе `null`; значения >1 сохраняются |
| Концентрация | Максимальная сумма одному получателю / `O`; при `O=0` — `null` |

Концентрация возвращается отдельной функцией контракта. При равных суммах
получатель выбирается лексикографически по gid. Например, 30 и 70 KZT
двум получателям дают 0.7. Суммы переводов не являются балансом счёта;
отношение не доказывает пересылку тех же денег.

## Предложение правил ролей

`F` означает одновременно `outbound_censored is false` и
`inbound_incomplete is false`: полнота подтверждена в пределах окна и фильтров.
Неизвестное значение не проходит проверку `F`.

| Роль | Все условия одновременно (AND) | Проходит / не проходит |
|---|---|---|
| coordinator | `ki >= 3`, `ko >= 3` | `(3,3)` / `(3,2)` |
| consolidator | `F`, `ki >= 3`, `1 <= ko <= 2`, `I > 0`, `0 < r <= 0.5` | `(3,1,r=.5,F)` / `r=.5001` |
| distributor | `F`, `ki <= 2`, `ko >= 3`, `I > 0`, `r >= 1.5` | `(1,3,r=1.5,F)` / `r=1.4999` |
| transit | `F`, `1 <= ki <= 2`, `1 <= ko <= 2`, `I > 0`, `0.8 <= r <= 1.25` | `(1,1,r=.8,F)` / `r=.7999` |
| terminal | `ki >= 1`, `I > 0`, `ko = 0`, `O = 0`, `outbound_censored is false` | полный узел без исходящих / тот же узел с неизвестной полнотой |
| peripheral | `F`, `ki + ko <= 2`, никакая более специфичная роль не подошла | изолированный узел с F / изолированный узел с неизвестной полнотой |

Порядок при конфликте: `coordinator > consolidator > distributor > transit > terminal > peripheral`.
Для `peripheral` условие суммы степеней выражается OR из трёх AND-групп:
`(ki<=1 AND ko<=1) OR (ki=0 AND ko<=2) OR (ko=0 AND ki<=2)`.
Так сохраняется фиксированный набор метрик контракта.

`role_score = 100`, если все условия выбранного правила выполнены.
Это бинарная мера соответствия, не вероятность и не уверенность в гипотезе.
Если ни одно правило неприменимо/не выполнено: `role=peripheral`,
`assignment_status=insufficient_evidence`, `role_score=0` и обязательное
пояснение недостаточности данных. Неизвестное условие имеет `passed=null`.

Coordinator здесь означает только наблюдаемый узел с несколькими входами
и выходами; организационное управление из такой структуры не следует.
Terminal — гипотеза внутри окна, фильтра и подтверждённой полноты обхода.
Строгие требования полноты могут оставить много узлов с недостаточными
основаниями. Это ожидаемый результат, а не повод заполнять неизвестное нулями.

## Предложение кластеризации

Louvain отдельно внутри каждой слабосвязной компоненты. Для алгоритма
используется неориентированная проекция с весом
`w(u,v)=tx_count(u,v)+tx_count(v,u)`. Направления сохраняются в выгрузках.
`resolution=1`, `threshold=1e-7`, `seed=42`; узлы и рёбра подаются в
отсортированном порядке, версия NetworkX фиксируется.
Одиночные узлы остаются отдельными кластерами. Нулевые веса не образуют
положительной связи для Louvain; при нулевой сумме весов выдаются singleton.
Ids компонент и кластеров вычисляются из отсортированных списков gid.

Назначение сообщества не следует из самого Louvain. Формальные гипотезы
должны ссылаться на правила и явно сохранять ограничения наблюдаемости.

Предлагаемый порядок гипотез (первое совпадение):

1. `n=1`: кластер из одного узла, назначение не установлено.
2. Есть coordinator: структура с двусторонним узлом сбора и распределения.
3. Доля transit `>=0.5`: гипотеза транзитной структуры.
4. Доля terminal `>=0.5`: гипотеза структуры получателей.
5. Иначе: устойчивое назначение не установлено.

В знаменателе долей все узлы, в том числе с недостаточными основаниями.
Кластер из одного узла не обязательно изолирован в исходном графе.
Каждая гипотеза ссылается на правило в rules.json. Ограничения включают
симметризацию, неполноту входа/выхода и то, что сообщество не доказывает
единую организацию.

## Предложение приоритета

Приоритет — порядок исследования наблюдаемого масштаба, не риск нарушения.
Пусть `V=I+O` (KZT), `K=ki+ko`, `T=tx_in_count+tx_out_count`.
Для каждого признака `N(x)=ln(1+x)/ln(1+max(x))`, где максимум берётся
по всем узлам запуска; при нулевом максимуме `N=0`.

`Q = 0.8 + 0.1*[outbound_censored is false] + 0.1*[inbound_incomplete is false]`.
Значение true или null не даёт бонуса подтверждённой полноты.

`priority_score = round(100 * Q * (0.45*N(V) + 0.30*N(K) + 0.25*N(T)), 4)`.

Сортировка: score убывает, при равенстве gid возрастает. Роль и role_score
в формуле не участвуют. Максимумы, исходные значения и флаги полноты
сохраняются как проверяемые основания; формула и веса — в rules.json.

## Масштабирование

Для порядка миллиона узлов: пакетная агрегация parquet с контролем точности,
компактные массивы графа вместо объектов Python, раздельная обработка компонент,
выдача подграфов по запросу. Тяжёлые графовые алгоритмы требуют отдельного
замера; текущая реализация не означает подтверждённой работы на таком объёме.
