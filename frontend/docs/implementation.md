# План C: реализация интерфейса

Контекст: изучены README, архитектура, контракт v1 и все четыре плана A–D, общий план интеграции. Исходная точка — коммит `6e9095d`. Работа ограничена `frontend/`, ветка `codex/frontend`.

## Последовательность

1. Типы контракта, HTTP-клиент, точное отображение gid и денежных строк.
2. Сценарий «поиск → ограниченный граф → карточка», топ-20 и кластеры.
3. Основания роли/приоритета, качество наблюдения, AI и экспорты.
4. Проверка отмены запросов, смены run_id, неизвестного и изолированного узла, сборка и браузерная проверка.

## Дизайн

Рабочее место аналитика: списки слева (280 px), гибкая область графа в центре, подробности справа (350 px). Верхняя строка сообщает состояние источника и идентификатор расчёта. На небольшом экране панели переходят в один столбец. Содержимое выровнено влево; числа используют табличные начертания.

Палитра: бумага `#ffffff`, фон рабочего поля `#f3f6fa`, текст `#172b46`, вторичный текст `#62748b`, действие `#245ec7`, предупреждение `#9a6115`. Роли используют отдельные цвета из общего словаря. Основной шрифт — системный Aptos/Segoe UI, без загрузки с CDN.

Главный визуальный элемент — направленный граф, всё остальное помогает выбирать узел и проверять основания. Роли различаются цветом и текстовыми подписями. Основания представлены таблицей; состояния отсутствия данных не заменяются вымышленными метриками. Проверка плана против брифа: три панели соответствуют плану C, декоративные KPI и рекламные блоки не нужны.

## Зависимости интеграции

На старте отсутствуют backend, `contracts/openapi.json`, общие фикстуры B и настоящие артефакты A. Потребитель реализуется по письменному контракту, без изменения полей и расчёта аналитических формул. Проверки фронтенда используют явно искусственные ответы исключительно в тестовой среде. Подключение к настоящему набору и проверка статики через FastAPI выполняются после готовности B.
